# Project plan: DeepSeek-V4-Flash-Vision-Exp, vLLM 3-card port, 3x CMP-170HX

Goal: get DeepSeek-V4-Flash-Vision-Exp running on the same 3-card vLLM setup as
`dsv4-flash-0731` ([[deepseek_v4_vllm_pp_dspark]], `PLAN-vllm-pp-dspark-3card.md`), matching
the same **GPU-fill methodology** (not a fixed context target — see Pre-flight below for
why) so 0731 stays the daily driver on cards 0-2 and the 4th card stays free for
ComfyUI/Blender, untouched, throughout.

Source: https://github.com/wtdcode/vllm-backport pull #58 (merged, closed) — adds
Vision-Exp support with 3 sm80-specific fixes, validated on **4x** CMP 170HX. This plan is
the 3-card port of that work.
Base engine: same lineage as 0731's `haosdent/vllm` fork (see that plan's header) — TBD
whether wtdcode's patches apply cleanly on top, or need re-basing; check before Phase 2.

Full research trail for everything below: `~/deepseek-v4-flash-vision-agent/README.md` +
`PLAN.md`, and memory `deepseek_v4_flash_vision_exp_project.md`.

## Pre-flight results (checked 2026-09-28, before committing to this)

- **Checkpoint size**: 156.31 GiB (48 shards) — barely bigger than 0731's 155.4 GiB.
  Confirmed via HF API, not estimated. Capacity was never really the blocker here.
- **Layer count**: `num_hidden_layers = 43`, identical to 0731, same `DeepseekV4ForCausalLM`
  architecture class. The vision tower is additive config only (`vision_n_layers`,
  `vision_dim`, etc.) — **0731's `VLLM_PP_LAYER_PARTITION=15,15,13` is the starting-point
  partition**, not a guess from scratch.
- **The 3 wtdcode sm80 fixes are rank-count-generic** — read the actual PR #58 diff, not
  just its description. Attention routing keys off `device_capability.major == 8` (per-GPU,
  not per-topology). PP relay threads `dsv4_img_ids` through vLLM's standard
  `IntermediateTensors`, gated on `get_pp_group().is_first_rank`/`is_last_rank` — vLLM's own
  rank abstraction, identical at any PP size. Vision attention math (bidirectional in-image
  visibility, workspace sizing) is per-token/per-request, orthogonal to topology. **Expect
  this to be a config/tuning exercise, not a code-porting one** — but not yet proven on real
  hardware, this is a code-reading conclusion, confirm empirically in Phase 2+.
- **NOT swappable with 0731's checkpoint**: verified by SHA256 (not just file size) that all
  48 shards differ between the two — Vision-Exp was made via continued training on top of
  0731, not a frozen base + bolted-on module. Every weight shifted, not just vision ones.
  Two full separate checkpoints on disk, no partial reuse.
- **Benchmarks**: Vision-Exp wins all 6 directly shared benchmarks against 0731, including
  text-only agent tasks (Terminal-Bench 2.1, DeepSWE edges past Opus-4.8, DSBench-Hard,
  NL2Repo) — not just vision-specific ones. Same `max_position_embeddings=1048576` as 0731
  (confirmed in both configs directly — an aggregator site's claim of a smaller output cap
  was wrong).
- **DSpark is NOT supported for Vision-Exp** — confirmed in the wtdcode diff: the weight
  loader strips MTP/DSpark weights outright, comment says as much explicitly. The 0731
  production script's `$SPEC` flag must be dropped entirely for this model, not just left
  as-is (it would fail to load, not silently no-op).
- **Known quality risk, not yet tested on our own config**: ik_llama.cpp issue #2464
  reports hallucinations/errors reading structured visual content (spreadsheet cells,
  column headers) on this exact checkpoint. Different engine (ggml, not vLLM) so may not
  transfer directly, but the underlying weights are the same — worth a cheap smoke test
  early (Phase 4 below) before investing further.

## Known risks/unknowns going in

- **3-card Ampere Vision-Exp is unverified anywhere** — wtdcode's numbers are all 4-card.
  We'd be the first data point at 3, same situation 0731's project was in against the
  4-card `allover326` source repo.
- **`gpu-memory-utilization` ceiling is unknown at 3 cards for this checkpoint.** 0731's own
  campaign found a hard cliff (0.965 safe / 0.97 crashes) with *zero* vision overhead —
  Vision-Exp's extra image-token KV cache could tighten that further. **Do not assume 0.965
  carries over — re-run the full binary-search stress test from scratch** (this is the
  explicit project goal per the 2026-09-28 conversation: match the fill *methodology*, let
  whatever context ceiling results be the honest answer, higher or lower than 0731's).
- **Partition is confirmed NOT a stability lever** (0731's own production script comments:
  all 3 PP ranks always land at identical fill % regardless of partition, tested and
  disproven). Don't waste time adjusting `VLLM_PP_LAYER_PARTITION` if the ceiling comes out
  different from 0731's — the levers that matter are `--gpu-memory-utilization` and
  `--max-model-len`.
- **PCIe Gen2 x4 bandwidth under vision-token load**: untested whether feeding image
  patches through the 3-card PP split (processed on whichever rank hosts the vision tower,
  then relayed) hits our known PCIe ceiling harder than pure text tokens. No data yet.
- Whether `sm80vllm` (the actively-maintained fork, vs. wtdcode's closed/merged PR) has
  picked up the Vision-Exp fixes needs checking again before Phase 2 — as of 2026-09-28 it
  hadn't (V4/GLM-5.3-Flash only). The weekly routine (`trig_01JFxfSzgMLEWSsJorM7ULjb`)
  watches this.

## Phase 1 — Build the image (patch merge DONE 2026-09-29, image build not yet run)

- `sm80vllm` re-checked: still no Vision-Exp support (same Aug 1 commit as before). Staying
  with `wtdcode/vllm-backport#58` as planned.
- **Notable discovery**: `wtdcode/vllm-backport` contains our exact base commit
  (`f8ea5bb16`) directly in its own history — same commit message even appears as
  `sm80vllm`'s latest commit too. All three (our `haosdent/vllm` base, `sm80vllm`, and
  `wtdcode/vllm-backport`) share direct lineage, not independent parallel efforts.
- Worked in an **isolated copy** (`vllm-dsv4/vllm-vision-exp-experiment/`), not the live
  tree that backs the working 0731 setup — safe to redo/discard if needed.
- PR #58's head branch (`pr/vision-sm80`, wasn't merged via GitHub's button — maintainer
  manually adopted it into `master` and closed the PR) is 822 commits diverged from our
  base, so a branch merge wasn't the right tool. Pulled the full PR diff (38 files) instead
  and applied it directly on top of our already-patched tree, same approach as the original
  0731 patches (0002-0006).
- **Result**: 29/38 files applied cleanly. 9 had real conflicts (`git apply --check`'s
  exit-0 was misleading here — the actual apply failed until resolved manually). All 9
  turned out tractable:
  - 8 files: purely additive on their side (our side empty) or a clean generalization that
    reduces to our existing behavior when there's no vision input — took theirs.
  - `vllm/config/vllm.py`: same frozenset, both sides added different model-class entries
    — resolved as a union (11 entries), not picking one side.
  - `vllm/models/deepseek_v4/nvidia/model.py`'s weight-loader conflict needed real
    judgment: our local patch skips `mtp.`-prefixed weights during loading
    (`skip_substrs=["mtp."]`) — necessary for 0731, which does ship MTP/DSpark weights.
    Took theirs (which drops that skip and calls `process_weights_after_loading()`
    directly) because we already confirmed Vision-Exp's checkpoint ships no MTP/DSpark
    weights at all — nothing to skip, the filter would just be dead code for this model.
- **Verified, not assumed**: zero conflict markers remain (`grep` confirmed), every
  modified `.py` file passes `python3 -m py_compile`. Not yet verified: that it actually
  builds and runs — syntax-valid isn't the same as correct.
